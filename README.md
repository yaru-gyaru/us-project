# JolTap — оптимизатор городских маршрутов

JolTap — веб-приложение для построения оптимального маршрута между несколькими адресами в Астане. Сервис предназначен для группы людей, которые едут вместе на одном автомобиле или заказном автобусе.

Пользователь указывает стартовую точку и адреса остановок. Приложение находит координаты адресов, рассчитывает расстояния по дорогам, подбирает порядок посещения и отображает готовый маршрут на карте.

## О проекте

При поездке по нескольким адресам порядок остановок сильно влияет на общую длину маршрута. Если посещать точки в порядке их добавления, поездка может оказаться длиннее необходимого.

JolTap решает эту задачу:

1. Принимает стартовую точку и список адресов.
2. Находит точки на карте.
3. Получает дорожные расстояния между ними.
4. Определяет выгодный порядок посещения.
5. Строит маршрут по улицам.
6. Показывает расстояние, время и экономию.

## Цель проекта

Разработать полноценное веб-приложение на Next.js, которое помогает организатору совместной поездки построить удобный маршрут по нескольким адресам в Астане.

Основной критерий оптимизации первой версии — минимальное расстояние по дорогам.

## Основной сценарий

1. Пользователь открывает приложение.
2. Выбирает вид транспорта: автомобиль или заказной автобус.
3. Указывает количество участников.
4. Вводит стартовый адрес.
5. Добавляет адреса остановок.
6. При необходимости меняет порядок, редактирует или удаляет точки.
7. Выбирает, нужно ли возвращаться к стартовой точке.
8. Нажимает кнопку «Рассчитать маршрут».
9. Приложение подбирает порядок посещения.
10. Пользователь получает маршрут на карте, расстояние, время и список остановок.

Все участники едут вместе в одном транспортном средстве. Приложение не распределяет людей по разным автомобилям или автобусам.

## Ограничения первой версии

В MVP поддерживается:

- Один организатор.
- Одно транспортное средство.
- Автомобиль или заказной автобус.
- Одна стартовая точка.
- До 20 точек, включая старт.
- Поездки только в пределах Астаны.
- Оптимизация по расстоянию.
- Сохранение последнего маршрута в браузере.

Демонстрационный сценарий использует шесть адресов: стартовую точку и пять остановок. Для пяти оставшихся точек существует 120 возможных порядков посещения:

```text
5! = 5 × 4 × 3 × 2 × 1 = 120
```

Для небольшого количества точек можно проверить все варианты или использовать точный алгоритм. Для больших маршрутов потребуется более быстрый приближённый алгоритм.

## Алгоритм оптимизации

### Входные данные

Алгоритм получает:

- стартовую точку;
- список остановок;
- матрицу расстояний;
- матрицу времени;
- настройку возвращения к старту.

### Матрица расстояний

Для каждой пары точек хранится дорожное расстояние:

```text
distance[A][B]
distance[B][A]
```

Эти значения могут отличаться из-за односторонних улиц, разворотов и дорожных ограничений.

### Небольшие маршруты

Для небольшого количества остановок используется точный алгоритм:

- полный перебор;
- либо динамическое программирование.

Алгоритм должен найти порядок с минимальной суммой дорожных расстояний при закреплённом старте.

### Большие маршруты

Для большого количества точек используется приближённый алгоритм:

1. Выбор ближайшей следующей точки.
2. Построение начального маршрута.
3. Улучшение порядка методом перестановок.
4. Сравнение с исходным порядком.
5. Возврат лучшего найденного варианта.

Если используется приближённый алгоритм, интерфейс показывает: «Найден подходящий маршрут». Формулировка «абсолютно лучший маршрут» не используется.

## Расчёт результата

Для каждого маршрута рассчитываются:

```text
Общее расстояние = сумма расстояний между соседними точками
Общее время = сумма времени движения между соседними точками
Экономия = исходное расстояние − новое расстояние
Экономия в процентах = экономия / исходное расстояние × 100%
```

Если включено возвращение к старту, в расчёт добавляется участок от последней остановки до стартовой точки.

## Проверка данных

Перед расчётом необходимо проверить:

- указана стартовая точка;
- добавлена хотя бы одна остановка;
- все адреса подтверждены;
- координаты имеют правильный формат;
- количество участников является положительным целым числом;
- количество точек не превышает технический лимит;
- транспорт имеет допустимое значение;
- точки расположены в пределах поддерживаемой территории.

Неподтверждённый текст адреса не должен отправляться на оптимизацию.

## Обработка ошибок

Приложение должно показывать понятные сообщения при следующих ситуациях:

- адрес не найден;
- маршрут между точками не существует;
- внешний сервис недоступен;
- превышен лимит запросов;
- соединение с интернетом потеряно;
- запрос выполняется слишком долго;
- введено неправильное количество участников;
- добавлено слишком много остановок;
- сервер вернул некорректные данные;
- маршрут был изменён во время расчёта.

При ошибке введённые пользователем данные не должны пропадать.

## Особенности автобусного режима

В проекте под автобусом понимается заказной автобус, который перевозит всю группу по одному маршруту.

Если выбранный сервис поддерживает специальный автобусный профиль, приложение должно учитывать доступные ограничения.

Если используется обычный автомобильный профиль, пользователю показывается предупреждение:

> Предварительный маршрут: ограничения по высоте, массе и проезду автобусов не учтены. Проверьте маршрут перед поездкой.

## Безопасность

- API-ключи хранятся только на сервере.
- Секретные данные не отправляются в браузер.
- Все входные данные проверяются.
- Для запросов устанавливается ограничение частоты.
- Пароли хранятся только в виде хеша.
- Доступ к сохранённым маршрутам проверяется по пользователю.
- Сообщения об ошибках не раскрывают внутренние данные сервера.

- точный и приближённый алгоритмы.

### Интеграционные тесты

Проверяются:

- поиск адресов;
- обработка ответа дорожного сервиса;
- сохранение маршрута;
- получение истории;
- обработка ошибок API.

### Пользовательские тесты

Проверяются сценарии:

1. Создание маршрута из шести адресов.
2. Изменение стартовой точки.
3. Выбор автомобиля.
4. Выбор автобуса.
5. Включение возвращения к старту.
6. Удаление остановки.
7. Восстановление маршрута после обновления.
8. Ошибка внешнего сервиса.
9. Работа на мобильном устройстве.

## Критерии готовности MVP

MVP считается завершённым, если:

- приложение запускается по инструкции;
- пользователь может выбрать транспорт;
- количество участников принимается без искусственного ограничения;
- можно добавить старт и минимум пять остановок;
- точки отображаются на карте;
- старт остаётся первой точкой;
- приложение получает дорожные расстояния;
- рассчитывается порядок посещения;
- маршрут строится по улицам;
- отображаются километры и время;
- показывается исходный и новый порядок;
- рассчитывается экономия;
- маршрут сохраняется после обновления страницы;
- ошибки отображаются без потери введённых данных;
- интерфейс работает на компьютере и телефоне;
- сборка проекта завершается без ошибок.
