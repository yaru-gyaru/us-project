SkillBarter — платформа обмена навыками и временем
1. Описание проекта
SkillBarter — веб-приложение, в котором пользователи обмениваются знаниями и услугами без использования денег.
Вместо обычной оплаты применяется внутренняя единица — час помощи:
1 час оказанной услуги = 1 час на балансе
Например, пользователь провёл один час занятия по Java и получил один час на внутренний баланс. Затем он может потратить этот час на изучение английского языка, консультацию дизайнера, помощь с математикой или другую услугу.
Обмен не обязательно происходит между двумя одинаковыми пользователями. Если Айару помогла Сымбат с программированием, заработанный час можно потратить на услугу любого другого участника платформы.
2. Проблема
У многих людей есть полезные знания и навыки, но нет возможности постоянно оплачивать обучение или профессиональные услуги. При этом они сами могут предложить другим пользователям собственную помощь.
Существующие платформы обычно предлагают:
платные курсы;
разовые услуги за деньги;
поиск репетиторов;
публикацию объявлений без безопасного механизма обмена.
SkillBarter создаёт систему, в которой главным ресурсом становится время пользователя.
3. Цель проекта
Разработать полноценную платформу обмена навыками, которая позволяет:
публиковать предложения услуг;
находить нужных специалистов;
договариваться о времени встречи;
резервировать часы;
подтверждать выполнение;
переводить часы между пользователями;
оставлять отзывы;
вести историю операций;
разрешать спорные ситуации.

7. Основной принцип внутреннего баланса
В системе используется внутренняя единица:
1 кредит = 1 час помощи
Для удобства расчёта баланс хранится в минутах:
60 минут = 1 кредит
30 минут = 0,5 кредита
90 минут = 1,5 кредита
В интерфейсе значение показывается в часах и минутах.
Стартовый баланс
После регистрации пользователь получает два стартовых часа:
Стартовый баланс: 120 минут
Стартовые часы позволяют новому пользователю получить первую услугу. Начисление выполняется только один раз.
В полноценной версии можно ограничить стартовые часы:
запретить их вывод;
разрешить потратить только после заполнения профиля;
отменять начисление для подозрительных повторных аккаунтов.
Денежная стоимость внутренним часам не назначается. Вывод часов в реальные деньги не поддерживается.
8. Основной пользовательский сценарий
Пользователь регистрируется.
Заполняет профиль.
Указывает навыки, которыми готов поделиться.
Создаёт предложение услуги.
Другой пользователь находит предложение через поиск.
Выбирает длительность и отправляет заявку.
Исполнитель принимает заявку.
Система резервирует необходимое количество минут заказчика.
Пользователи согласовывают дату и формат встречи.
Исполнитель оказывает услугу.
Обе стороны подтверждают выполнение.
Зарезервированные минуты переводятся исполнителю.
Пользователи оставляют отзывы.
9. Жизненный цикл заявки
Каждая заявка проходит через определённые состояния:
Создана
   ↓
Ожидает ответа
   ↓
Принята
   ↓
Запланирована
   ↓
Выполняется
   ↓
Ожидает подтверждения
   ↓
Завершена
Альтернативные состояния:
Отклонена
Отменена
Просрочена
Открыт спор
Возврат часов
Правила переходов
Только заказчик создаёт заявку.
Только исполнитель принимает или отклоняет её.
После принятия часы резервируются.
До начала встречи заявка может быть отменена согласно правилам.
После завершения исполнитель отправляет запрос на подтверждение.
Заказчик подтверждает выполнение.
После подтверждения часы переводятся исполнителю.
Если стороны не согласны, создаётся спор.
Во время спора зарезервированные часы нельзя использовать.
10. Функциональные требования
10.1. Регистрация и авторизация
Пользователь может:
зарегистрироваться по имени, электронной почте и паролю;
войти в аккаунт;
выйти из аккаунта;
восстановить пароль;
подтвердить электронную почту;
изменить пароль.
Требования:
электронная почта должна быть уникальной;
пароль хранится только в виде хеша;
защищённые страницы доступны только после входа;
заблокированный пользователь не может создавать новые заявки.
10.2. Профиль пользователя
Профиль содержит:
имя;
фотографию;
город;
краткое описание;
языки общения;
список навыков;
формат работы;
рейтинг;
количество завершённых обменов;
дату регистрации;
статус подтверждения;
доступное время.
Форматы работы:
онлайн;
офлайн;
онлайн и офлайн.
Пользователь может скрыть точный адрес. До подтверждения встречи другим пользователям показывается только город или район.
10.3. Предложения услуг
Пользователь может создать предложение, указав:
название;
описание;
категорию;
уровень;
формат;
город;
минимальную длительность;
максимальную длительность;
доступные дни;
необходимые материалы;
изображение;
язык оказания услуги.
Пример:
Название: Помогу разобраться с основами Java
Категория: Программирование
Уровень: Начальный
Формат: Онлайн
Длительность: 60–120 минут
Язык: Русский или казахский
Пользователь может:
редактировать предложение;
временно отключать его;
удалять предложение;
просматривать количество просмотров;
видеть входящие заявки.
10.4. Поиск
Поиск должен поддерживать:
текстовый запрос;
категории;
город;
онлайн или офлайн;
язык;
рейтинг;
уровень;
длительность;
доступность по дням;
сортировку.
Варианты сортировки:
по соответствию;
по рейтингу;
по популярности;
сначала новые;
по ближайшему доступному времени.
10.5. Заявки
При создании заявки заказчик указывает:
выбранное предложение;
желаемую длительность;
предполагаемую дату;
формат встречи;
сообщение исполнителю.
Перед созданием заявки сервер проверяет:
пользователь не заказывает собственную услугу;
предложение активно;
исполнитель не заблокирован;
длительность соответствует условиям;
у заказчика достаточно доступных часов;
выбранное время ещё не занято.
10.6. Бронирование часов
После принятия заявки необходимое количество минут переводится из доступного баланса в резерв.
Пример:
Общий баланс: 180 минут
Заявка: 60 минут
Доступно после резерва: 120 минут
В резерве: 60 минут
После завершения:
Заказчик: −60 минут
Исполнитель: +60 минут
Резерв: 0 минут
При разрешённой отмене минуты возвращаются заказчику.
Баланс запрещено изменять обычным обновлением поля пользователя. Каждое начисление и списание должно создавать отдельную запись в журнале операций.
10.7. Чат
Для каждой принятой заявки создаётся отдельный чат.
В чате можно:
отправлять текстовые сообщения;
видеть время отправки;
видеть статус прочтения;
отправлять системные уведомления;
обсуждать дату и формат;
получить ссылку на онлайн-встречу.
В MVP загрузка файлов в чат необязательна.
Системные сообщения:
Заявка принята
Время встречи изменено
60 минут зарезервировано
Исполнитель отметил услугу выполненной
Заказчик подтвердил выполнение
Открыт спор
10.8. Календарь
Пользователь может:
указать свободные дни и часы;
просмотреть запланированные встречи;
принять предложенное время;
предложить другое время;
отменить встречу;
получать напоминания.
Система не должна позволять пользователю одновременно участвовать в двух встречах.
10.9. Завершение обмена
После встречи исполнитель нажимает «Услуга оказана».
Заказчик получает варианты:
подтвердить выполнение;
сообщить о проблеме;
открыть спор.
После подтверждения:
резерв переводится исполнителю;
заявка получает статус «Завершена»;
обеим сторонам открывается форма отзыва;
операция добавляется в историю баланса.
10.10. Отзывы
Отзыв содержит:
оценку от 1 до 5;
текстовый комментарий;
дату;
информацию о завершённой сделке.
Правила:
отзыв можно оставить только после завершённого обмена;
по одной заявке каждая сторона оставляет один отзыв;
пользователь не может оценить себя;
отзыв связан с реальной заявкой;
администратор может скрыть отзыв после жалобы;
рейтинг пересчитывается сервером.
10.11. Жалобы и споры
Пользователь может открыть спор, если:
исполнитель не пришёл;
заказчик не подтвердил выполнение;
услуга не соответствует описанию;
встреча не состоялась;
пользователь нарушал правила поведения.
Спор содержит:
причину;
описание;
сообщения сторон;
дату создания;
решение администратора;
статус;
сумму зарезервированного времени.
Решения администратора:
перевести часы исполнителю;
вернуть часы заказчику;
разделить часы между сторонами;
закрыть спор без изменения;
вынести предупреждение;
заблокировать пользователя.
Любое решение администратора записывается в журнал.
10.12. Избранное
Пользователь может:
добавить предложение в избранное;
удалить его из избранного;
просматривать сохранённые предложения;
получать уведомление, если предложение снова стало доступно.
10.13. Уведомления
Система создаёт уведомления при событиях:
получена новая заявка;
заявка принята;
заявка отклонена;
изменено время встречи;
приближается встреча;
услуга отмечена выполненной;
требуется подтверждение;
получен новый отзыв;
открыт спор;
спор рассмотрен;
получено новое сообщение.
Каналы:
уведомления внутри приложения;
электронная почта;
push-уведомления в будущей версии.
11. Система рекомендаций
Система может предлагать услуги на основе:
указанных интересов;
навыков пользователя;
истории поиска;
просмотренных предложений;
города;
формата работы;
рейтинга исполнителя;
свободного времени.
В MVP используется обычная система баллов:
Совпадение категории          +30
Подходящий город              +20
Онлайн-формат                 +15
Подходящее время              +15
Высокий рейтинг               +10
Новое предложение             +5
Популярное предложение        +5
Предложения сортируются по итоговому баллу.
Применение искусственного интеллекта не является обязательным для MVP.
12. Прямой и цепочный обмен
Обычный обмен
Пользователь получает услугу и оплачивает её внутренними часами.
Айару → помогает Сымбат с Java
Сымбат → переводит Айару 60 минут
Цепочный обмен
Заработанные часы можно потратить у любого участника:
Айару помогает Сымбат с Java
Сымбат помогает Баянсулу с английским
Баянсулу помогает Айару с дизайном
Платформа не должна заранее строить замкнутую цепочку. Общий баланс времени автоматически обеспечивает такой обмен между разными пользователями.

20. Требования к операциям с балансом
Операции с внутренними часами должны выполняться внутри транзакции базы данных.
При принятии заявки сервер должен:
Проверить статус заявки.
Проверить доступный баланс.
Заблокировать нужные записи на время операции.
Уменьшить доступный баланс.
Увеличить зарезервированный баланс.
Создать запись операции.
Изменить статус заявки.
Зафиксировать транзакцию.
Если один из шагов завершился ошибкой, все изменения отменяются.
Каждая финансовая операция должна иметь уникальный ключ идемпотентности. Повторный запрос не должен дважды списывать или начислять минуты.
Баланс пользователя не может стать отрицательным.
21. Проверка данных
Backend должен проверять:
формат электронной почты;
длину пароля;
обязательные поля;
допустимую длительность;
существование предложения;
права пользователя;
статус предложения;
статус заявки;
доступный баланс;
отсутствие конфликта расписания;
допустимость перехода между статусами;
отсутствие повторного отзыва;
размер загружаемого изображения.
Проверка на frontend используется для удобства. Главная проверка всегда выполняется на сервере.
22. Безопасность
Пароли хранятся в виде хеша.
Сессии защищены.
Все действия проверяют роль пользователя.
Пользователь не может изменять чужие предложения.
Пользователь не может самостоятельно увеличивать баланс.
Все операции с балансом журналируются.
API имеет ограничение частоты запросов.
Загружаемые файлы проверяются по типу и размеру.
HTML из сообщений очищается.
Личная информация не показывается без необходимости.
Администраторские действия записываются в журнал.
Секретные ключи хранятся в переменных окружения.
23. Нефункциональные требования
Адаптивность от 360 пикселей.
Основные страницы загружаются не более трёх секунд при нормальном соединении.
Ошибка одного внешнего сервиса не должна повреждать пользовательские данные.
Все даты хранятся в UTC.
Пользователь видит время в своём часовом поясе.
Списки используют пагинацию.
Изображения оптимизируются.
Формы доступны с клавиатуры.
Ошибки обозначаются текстом, а не только цветом.
Код проходит проверку типов и сборку.

полноценная социальная сеть.
25. Критерии готовности MVP
Проект считается готовым, если:
Пользователь может зарегистрироваться и войти.
После регистрации один раз начисляется стартовый баланс.
Пользователь может заполнить профиль.
Пользователь может создать и опубликовать услугу.
Другой пользователь может найти эту услугу.
Нельзя заказать собственное предложение.
Заказчик может отправить заявку.
Исполнитель может принять или отклонить её.
После принятия часы резервируются.
Повторный запрос не приводит к повторному списанию.
Баланс не может стать отрицательным.
Пользователи могут вести переписку по заявке.
После подтверждения часы переводятся исполнителю.
Операция появляется в истории обеих сторон.
После завершения можно оставить отзыв.
Нельзя оставить отзыв без завершённой заявки.
При споре часы остаются в резерве.
Администратор может разрешить спор.
Интерфейс работает на телефоне и компьютере.
Проект успешно собирается и проходит основные тесты.
